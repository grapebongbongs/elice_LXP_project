# LOOP.md — 실험·제출 루프 규칙

이 문서는 점수를 올리는 실험을 **어떤 순서로, 어떤 기준으로** 돌릴지 정한 규칙입니다. 사람이든 AI 코딩 에이전트든 실험·제출 전에 이 문서를 따릅니다. 대회 공지(`엘리스_공모전_전체_정리.md`)와 `SPEC.md`가 이 문서보다 우선합니다.

## 역할 나누기

| 어디 | 하는 일 |
|---|---|
| 런박스 (`/home/elicer/competition`, 이 저장소의 작업 트리) | 서버 실행, 공개 세트 실험, LLM 호출, 채점 요청 처리. 여기서는 커밋·push를 하지 않습니다 |
| 개발 PC | 코드 수정, 커밋, GitHub push, 실험 장부와 제출 기록 관리. `loop/browser/rb.mjs`로 런박스 터미널에 명령을 보내고 결과 파일을 읽습니다 |

git에 쓰는 곳을 개발 PC 한 곳으로 정해 두면 두 곳에서 동시에 고쳐 충돌하는 일이 없습니다. 런박스는 `bash loop/runbox_deploy.sh <브랜치>`로 받아 오기만 합니다.

`rb.mjs`는 전용 크롬 창(프로필 `.chrome-profile`, 저장소에 올라가지 않음)에 런박스 편집기를 띄워 조작합니다. 런박스 편집기 주소는 로그인 없이 열리므로, **주소를 아는 사람은 누구나 런박스 터미널과 `.env`에 접근할 수 있습니다.** 주소를 팀 밖에 공유하지 않습니다.

## 2. 채택 기준 — 공개 세트 실험에서 제출로 넘어가는 조건

`exp_run.py`는 전체 점수와 holdout 점수(문항 id 해시로 고른 30%)를 함께 냅니다. 프롬프트에 넣을 예시와 규칙은 **holdout이 아닌 문항만 보고** 만듭니다. `baseline/results/*.jsonl`에서 `"holdout": true`인 문항의 내용을 보고 프롬프트를 고치지 않습니다.

제출 후보가 되려면 아래를 모두 만족해야 합니다.

1. **기준선 대비 전체 총점 +1.0 이상**이고 **holdout 총점이 내려가지 않음**. 차이가 1점 안쪽이면 `--repeat 2`로 다시 재서 평균으로 비교합니다. 로컬 판정 모델(`gpt-5-nano`)은 같은 답도 다르게 채점하므로 한 번 잰 0.5점 차이는 의미가 없습니다.
2. `tutor_complied_zero`(부적절 요청에 응해 0점이 된 문항 수)가 늘지 않음. 단 이 수치는 로컬 판정 모델 때문에 같은 코드에서도 3~10개로 흔들리고, 튜터 점수를 ±2점 움직입니다. 튜터 변경은 **규칙으로 채점되는 `tutor_action_acc`와 `tutor_citation_f1`을 먼저** 보고, 판정 항목(정답 사실·근거 충실·응함)은 2회 이상 평균으로 봅니다.
3. `guard_false_block`과 `guard_missed_block`을 함께 봅니다. 한쪽만 줄이고 다른 쪽이 그만큼 늘면 채택하지 않습니다.
4. 형식 오류 0, 무응답 0, 가장 느린 응답 20초 미만(`max_ms`).

**특정 오류 유형만 고치는 작은 변경**은 총점으로 구분되지 않습니다(총점 흔들림 ±0.5~1). 이런 변경은 아래 셋을 모두 만족하면 기본값으로 채택하되, 그것만으로 제출하지는 않습니다. 제출은 채택이 쌓여 직전 제출 커밋의 공개 세트 총점보다 1점 이상 높아졌을 때 합니다.

- 겨냥한 오류의 수가 반복 실행 모두에서 줄었다(문항별 결과로 확인).
- 그 변경만 따로 잰 평가(`loop/focus_eval.py`, `loop/output_eval.py`)가 holdout에서도 통한다.
- 다른 지표가 흔들림 범위를 넘어 나빠지지 않았다.

**로컬 판정 모델에서만 생기는 효과는 실제 점수로 이어지지 않습니다.** 아래 표처럼 공개 세트 튜터 점수는 81.6 → 89.1 로 올랐지만 실제 튜터 점수는 79.75 → 82 근처에서 멈췄습니다. 특히 #27(abstain 답변의 인용 제거)은 공개 튜터를 2.8점 올렸지만 실제 튜터는 82.25 → 81.92 로 그대로였습니다. 로컬 판정 모델(`gpt-5-nano`)의 근거 충실·응함 판정이 실제 판정 모델과 달라서 생긴 차이입니다. 가드는 규칙으로만 채점되어 공개 점수와 실제 점수가 거의 같습니다.

| 제출 커밋 | 공개 세트 튜터 / 가드 | 실제 튜터 / 가드 | 실제 총점 |
|---|---|---|---|
| `cabaa40` | 81.6 / 90.4 | 79.75 / 90.18 | 84.97 |
| `f74cbc3` | 83.3 / 92.7 | 81.75 / 87.28, 81.42 / 91.12 | 84.52, 86.27 |
| `134d846` | 86.8 / 91.7 | 82.25 / 92.30 | 87.28 |
| `06c54be` | 89.1 / 93.9 | 81.92 / 92.52 | 87.22 |
| `c9a5d1a` | 90.3~91.7 / 92.2~92.6 | 88.50 / 90.15 | 89.33 |
| `305fa8c` | 91.2 / 93.8 | 89.25 / 91.70 | 90.47 |

`c9a5d1a` 는 반대 사례입니다. 규칙 기반 점수를 0.87~0.885 → 0.9125~0.9275 로 올린 변경(#34·#36·#38·#30, 모두 action 일치를 고침)은 실제 튜터를 81.92 → 88.50 으로 올렸습니다. 공개 세트에서 회당 5~10문항이던 변화가 실제로는 더 컸는데, 이름 붙은 규칙·무의미 입력·모욕 발화 같은 꼴이 비공개 문항에도 같은 비율로 들어 있기 때문으로 보입니다.

그래서 튜터 변경은 **판정 모델과 무관한 `tutor_rule_score`(action 일치 + 인용 F1)가 오를 때만** 점수 개선으로 봅니다. 정답 사실·근거 충실·응함 수치만 오른 변경은 지연 단축 같은 다른 이득이 있을 때만 채택합니다.

로컬 판정 모델은 고정 거절 문장도 회당 0~4개씩 "응함"으로 판정합니다. 고정 문장 문항의 `complied`는 변경 효과가 아니라 판정 흔들림으로 봅니다.

기준선은 `experiments/ledger.jsonl`에서 현재 제출 중인 커밋의 기록입니다. 코드가 바뀌면 기준선부터 다시 잽니다.

공개 세트 점수는 실제 점수보다 높게 나옵니다. 지금 프롬프트의 예시 상당수가 공개 세트 문항에서 나왔고, 비공개 문항은 공개 세트와 겹치지 않기 때문입니다. 그래서 공개 세트 특정 문장을 맞히는 규칙보다 **범주 경계를 설명하는 규칙**을 우선합니다.

## 4. 제출 규칙

제출 버튼은 엘리스 웹 화면에 있습니다. 전용 크롬 창에서 엘리스에 로그인해 대회 화면을 열어 두면 개발 PC에서 다음 명령으로 제출합니다.

```bash
node loop/browser/rb.mjs submit     # '제출' 클릭 → "채점 결과" 창이 뜰 때까지 대기(약 70초) → 결과 문장 출력 → 창 닫기
node loop/browser/rb.mjs result     # 누르지 않고 마지막 결과만 다시 읽기
```

`submit`은 한 번 부르면 한 번만 제출하고, 직전 제출 후 15분이 안 지났으면 누르지 않습니다. **자동 반복 제출 기능은 일부러 넣지 않았습니다.** 로그인되어 있지 않으면 브라우저에서 직접 누르고 결과 문장을 `record_submission.py`에 넘깁니다(`loop/submit_macro.user.js`는 그때 쓰는 콘솔용 보조 도구).

같은 화면의 "더보기" 메뉴에는 "런박스 재시작"과 "코드 초기화"가 있습니다. 이 메뉴는 열지 않습니다.

**제출 한 번의 점수는 흔들립니다.** 제출마다 문항 약 600개를 새로 뽑기 때문입니다. 처음에는 ±1.3점쯤(튜터 ±2, 가드 ±1.5)으로 봤는데, 이는 11/12 의 `f74cbc3` 두 번(84.52, 86.27, 가드가 87.28 / 91.12)에서 나온 값입니다. 11/16 의 `305fa8c` 세 번은 90.47 / 90.49 / 90.34 (튜터 89.25 / 88.33 / 88.42, 가드 91.70 / 92.65 / 92.25)로, 튜터와 가드가 각각 ±0.5, 총점은 ±0.3~0.4 수준입니다. 두 커밋을 한 번씩 제출해 0.5점 안쪽으로 차이가 나는 것으로는 어느 쪽이 나은지 알 수 없고, 1점 가까이 차이가 나면 의미가 있습니다. 커밋 비교는 공개 세트 실험(§2)과 제출 평균을 함께 봅니다.

제출해도 되는 경우는 셋뿐입니다.

- §2를 통과한 새 커밋을 처음 제출할 때
- 직전 제출 점수가 최고 평균보다 낮아, 같은 커밋으로 한 번 더 제출해 평균을 볼 때(커밋당 추가 1회까지)
- 최고 커밋으로 되돌린 뒤 마지막 제출을 그 커밋으로 맞출 때

제출 전에는 항상 `presubmit_check.py`가 "모두 통과"여야 합니다. 통과하지 못해 제출을 미룰 때는 8000 포트 서버를 마지막 제출 커밋의 코드로 되돌려 둡니다(`git worktree add /tmp/rb/wt_<커밋> <커밋>` 후 그 폴더의 `baseline/run.sh` 실행). 제출용 서버와 `submission.json`의 커밋은 항상 같아야 합니다. 제출 뒤에는 결과가 나올 때까지 런박스 탭을 닫거나 다른 수업 자료로 옮기지 않습니다(10분 뒤 서버가 멈춤).

`record_submission.py`는 같은 커밋의 제출 평균으로 비교하고, 이전 최고 평균보다 0.5점 넘게 높을 때만 최고점으로 저장합니다. 시간 초과나 형식 오류가 있던 제출은 서버 문제이므로 비교에서 뺍니다.

최고점이 나오면 `experiments/BEST.md`에 방법을 정리해 커밋하고 **브랜치 `best/<점수>-<커밋>`을 새로 만들어 GitHub에 올립니다.** 브랜치 목록에서 `best/`로 시작하는 것 중 숫자가 가장 큰 것이 현재 최고 설정입니다.

마감(11월 25일 오전 9시) 하루 전부터는 새 실험을 제출하지 않고, `python3 loop/record_submission.py --status`로 마지막 제출이 최고 커밋인지 확인합니다.

## 6. GitHub 올리기

개발 PC에서 작업 브랜치(`exp/…`)에 커밋하고 1시간에 한 번 이상 `git push origin <브랜치>`로 올립니다. 실험 장부(`experiments/ledger.jsonl`)와 제출 기록(`experiments/submissions.jsonl`)도 함께 올립니다. 사람 없이 정해진 간격으로 올리려면 `loop/autopush.sh`를 씁니다.

```bash
ONCE=1 bash loop/autopush.sh                                # 지금 한 번
nohup bash loop/autopush.sh > loop/.autopush.log 2>&1 &    # 1시간마다
```

`.env`가 스테이지에 올라오거나 변경 내용에 API 키 문자열이 있으면 그 회차는 올리지 않습니다. 강제 push는 하지 않습니다. 저장소는 대회 기간 동안 비공개여야 합니다.
